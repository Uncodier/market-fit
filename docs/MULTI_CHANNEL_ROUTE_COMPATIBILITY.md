# Legacy message routes in the multi-agent plan

Reviewed 2026-11-19 in the local market-fit, API, Workflows and Script checkouts.
This is a companion to the [multi-channel requirements](MULTI_CHANNEL_MULTI_AGENT_REQUIREMENTS.md).
The observations below describe current code. The routing rules and rollout gates are requirements, not deployed behavior.

**Zavu delivery follow-up:** the [repair and cutover guide](../../API/docs/CHANNEL_MESSAGE_ADMISSION.md) supersedes the original failure observations for pinned inbound delivery. Do not enable traffic on mixed old/new claim writers or interpret a reconciliation acknowledgement as provider delivery.

## HTTP contracts to keep

| Entry point | Current behavior | Required behavior during migration |
| --- | --- | --- |
| [`POST /api/agents/customerSupport/message`](../../API/src/app/api/agents/customerSupport/message/route.ts) | Used directly and by the worker. With a known site and no `agentId`, it looks up the newest active Support agent. Its [command builder](../../API/src/app/api/agents/customerSupport/message/generate.ts) fixes the role and tools to Customer Support even when given another ID. | Keep the URL and response shape. For channel traffic, resolve the connection and run the **effective agent's** instructions and allowed tools. A legacy `agentId` derived from a role lookup is not an override. Keep authorized, explicitly directed service calls distinct from channel traffic; missing or conflicting context is not authority to pick an agent. |
| [`POST /api/workflow/customerSupport`](../../API/src/app/api/workflow/customerSupport/route.ts) | The [widget](../../Script/src/chat/CustomerSupportService.ts) posts here. The API derives identity from the visitor session, drops the browser's `agentId`, starts Temporal, and by default waits for the final reply. `Prefer: respond-async` returns `202`; an authorized non-browser service also receives `202`. | Keep both modes, payloads, status codes and receipt IDs. Route the site's one web connection on the server. A `202` is admission, not a reply or proof of delivery. Web replies stay on web. |
| [`POST /api/workflow/customerSupport/status`](../../API/src/app/api/workflow/customerSupport/status/route.ts) | Re-derives the workflow ID from the authorized site/session, client message ID and original message. Returns running or the completed workflow result; terminal failure is `422`, unavailable status is `503`. | Poll only the original execution under the same visitor authorization; do not POST another message. Do not substitute the separate [`GET /api/agents/customerSupport/status?commandId=…`](../../API/src/app/api/agents/customerSupport/status/route.ts), which reports **command**, not workflow, status. |
| [`POST /api/agents/chat/message`](../app/api/agents/chat/message/route.ts) | The workspace proxy derives the agent from a persisted internal conversation and rejects an external conversation or absent assignment (`409`). The [backend](../../API/src/app/api/agents/chat/message/route.ts) requires `agentId`. | Preserve the distinction: direct chat addresses that authorized agent or returns an error. Neither Customer Support nor an external sender is a fallback. A human reply to an external conversation remains an explicit [intervention](../app/api/agents/chat/intervention/route.ts). |
| [`POST /api/workflow/agentMessage`](../../API/src/app/api/workflow/agentMessage/route.ts) | Requires `message`, `agentId` and `site_id`; waits for `agentMessageWorkflow` and returns its result. | Keep explicit authorized targeting and synchronous result/error semantics. Never retry a failed agent workflow by calling Customer Support. Verify worker registration before relying on it (below). |
| [`POST /api/agents/sales/message`](../../API/src/app/api/agents/sales/message/route.ts) and [`POST /api/agents/cmo/message`](../../API/src/app/api/agents/cmo/message/route.ts) | These are role-specific commands, with their own role lookup when `agentId` is absent. | Keep direct requests role-specific; neither role lookup nor a placeholder ID may determine which agent serves a channel. If several instances of a role qualify, require an explicit authorized target or a documented deterministic role default. |

[`POST /api/agent/message`](../../API/src/app/api/agent/message/route.ts) is the channel admission endpoint in the local API checkout, not an alias for direct chat. Inventory externally configured callers before cutover.

## Integration contract: migrate callers before changing the responder

**Local checkpoint, 2026-11-20:** Zavu is the first adapter. Its registered callback and the neutral URL share signature verification, event claims, sender/connection resolution and [one workflow handoff](../../API/src/lib/services/channels/admit-message.ts) in-process. There is no loopback fetch or second workflow. Keep the callback registered: it also owns non-message events. The neutral HTTP route currently accepts signed Zavu message envelopes only. See the [API contract and retry limits](../../API/docs/CHANNEL_MESSAGE_ADMISSION.md).

Immediate Zavu replies now [verify the original sender from the saved turn](../../API/docs/CHANNEL_MESSAGE_ADMISSION.md#reply-on-the-original-connection), rather than picking the first matching channel. Offline two-connection tests cover WhatsApp, Telegram, Instagram and email; real delivery is unverified. Other providers have not migrated. The widget's send/status contracts and the worker's execution URL are unchanged. The [per-connection settings](MULTI_CHANNEL_MULTI_AGENT_REQUIREMENTS.md#settings--agent-channels) store a preference only; they do not activate agent routing or grant tools.

**Target:** provider webhook → provider-specific verification and normalization → `POST /api/agent/message` → existing Customer Support admission/workflow → existing responder → original delivery channel. Keep the provider's registered callback URL, signature verification and acknowledgement contract. Change the adapter's next hop: submit the verified message once to the neutral endpoint, not to a role-specific route or directly to the workflow service. The endpoint authenticates the adapter and validates its site, connection and event identity.

1. **Introduce the facade first.** Delegate internally to the existing admission and execution services. Do not issue a client-visible redirect, copy Support logic, or dual-write during migration. An already-admitted turn in the [shared worker activity](../../Workflows/src/temporal/activities/sendCustomerSupportMessageActivity.ts) or [Outstand activity](../../Workflows/src/temporal/activities/outstandActivities.ts) must invoke the shared execution path, **not** POST back to workflow admission. One event has one workflow owner and one responder.
2. **Migrate and verify consumers.** Use the provider inventory below as the starting checklist. Track each adapter, worker, externally configured caller and documented example with its current destination, target, migration status and parity evidence. Update integration guides and API examples to show the neutral endpoint for channel admission and label the old route compatibility-only. Do not retire it until remaining traffic is identified and accounted for.
3. **Change internals later.** Bind the effective agent's background, context and existing authorized tools in the single responder. Moving it out of `customerSupport` must not require an integration to change URLs again.

**Widget exception:** the browser keeps `/api/workflow/customerSupport` and its status endpoint, not the legacy message URL. Preserve visitor-session authorization and reuse the same admission service behind that public contract. Workspace direct chat and provider-side Voice calls are not message webhooks.

## How a channel turn reaches delivery

1. **Admit and resolve.** The [business workflow service](../../API/src/lib/services/workflow/business-workflow-service.ts) starts `customerSupportMessageWorkflow` or submits it through [conversation ingress](../../API/src/lib/services/workflow/conversation-ingress.ts) when it has a FIFO scope. Provider adapters can call this service without hitting `/api/workflow/customerSupport`. Resolve the exact connection from authenticated provider/session data before looking up history, running guidance or selecting a responder. Preserve per-conversation ordering, not a site-wide queue.
2. **Select once.** Apply the conversation ownership/transfer policy. For a new conversation, use the connection's explicit same-site agent; only a known, unassigned connection may use the site's active canonical Support. If the assigned agent is missing/inactive, or an unassigned connection has no active canonical Support, save the verified inbound message once without a reply or tools. An identity mismatch, ambiguous connection or lookup failure is not an unassigned channel. Record the reason without attaching the event to a guessed conversation.
3. **Generate once.** The [worker](../../Workflows/src/temporal/workflows/customerSupportWorkflow.ts) selects a web, legacy WhatsApp, generic-channel or email branch. Eligible branches run bounded guidance and call the [support activity](../../Workflows/src/temporal/activities/sendCustomerSupportMessageActivity.ts), which POSTs to the direct message API. Direct HTTP calls do not run Temporal guidance inline. Keep one response owner: the inner route must not start the outer workflow again. Persist the resolved agent, connection and original event identity with the turn, including when the URL is still named `customerSupport`.
4. **Deliver or suppress.** Web returns a reply to the widget. [Generic channel](../../Workflows/src/temporal/workflows/channelCustomerSupportWorkflow.ts), legacy WhatsApp and [email](../../Workflows/src/temporal/workflows/emailCustomerSupportWorkflow.ts) branches can start separate send workflows; some pass the input `baseParams.agentId`, not the agent used to generate the reply. Bind delivery and attribution to the recorded turn and original sender. Recheck license, activation, human pause/takeover and approval immediately before sending. A generated reply, saved draft or successful parent workflow is not confirmation of provider delivery.

## Rollout gates

The [offline review](MULTI_AGENT_REVIEW_2026-11-20.md) reproduced unresolved delivery acknowledgement, fallback identity and media revalidation failures. These block cutover even when ordinary route/worker tests pass.

- **Destination and parity.** For each migrated webhook, assert its authenticated adapter submits to the new endpoint and does not also start a workflow. Replay the provider event: same receipt and no second generation or send. Compare pre- and post-migration sender, persistence, reply or suppression, and retry outcome. Verify worker execution never re-enters admission, and verify the widget's unchanged POST/status contract separately.

- **Unchanged-caller test (AC-31).** Send an event to number A with the existing webhook and no `agentId` after migration: canonical Support responds from A. Reassign A to Sales; send a distinct event in a fresh conversation with the same payload format: Sales responds from A, while B remains on Support. Replay the first event: recover its original outcome, not a Sales turn. Repeat with two mailboxes. Test missing inbox/number identity with both present: no guessed send.
- **Transport gaps.** The worker's generic dispatch condition does not include `sms`; unmatched inputs fall through to the email branch. Zavu admission now preserves verified SMS/unknown-channel history without starting that branch. Require an explicit verified adapter and original-channel delivery test before enabling SMS replies.
- **Retry identity.** The [web status key](../../API/src/app/api/workflow/customerSupport/request-contract.ts) uses the original client message ID and text. The send route accepts older payloads without that ID and can generate a new one; some provider adapters also generate a new workflow ID per attempt. Keep those requests valid, but do not claim a new ID deduplicates a retry. Use a verified provider event or persisted receipt when available; if an earlier send cannot be identified, reconcile it rather than automatically replaying the body.
- **Saved-only versus failure.** The [worker skip contract](../../Workflows/src/temporal/workflows/helpers/disabledCustomerSupport.ts) recognizes a persisted disabled result with conversation and inbound message IDs. Today the final-reply HTTP branch returns `502 WORKFLOW_NO_REPLY` for a completed result without assistant content, and `504 WORKFLOW_PENDING` if its wait expires. Specify and test how the widget recognizes a *persisted, intentionally skipped* turn in both response modes (additive or negotiated compatibility); keep a genuinely empty result an error. A timeout does not cancel Temporal: reconcile the same identified turn, never launch another agent, send or charge.
- **Worker and rollout compatibility.** The API requests `agentMessageWorkflow`, but no matching implementation/export was found in the inspected [worker source](../../Workflows/src/temporal/workflows/worker-workflows.ts). Verify the registered type and task queue in authorized nonproduction; route presence is not evidence it runs. Version workflow changes for replay of old histories. Enable reassignment only after all relevant ingress and send paths honor it. If rollout pauses, keep recorded turn identities and stop unsupported automation rather than reverting reassigned traffic to Support.

Baseline regressions: [web POST](../../API/src/app/api/workflow/__tests__/customer-support-async.test.ts), [status](../../API/src/app/api/workflow/__tests__/customer-support-status.test.ts), [workspace proxy](../__tests__/api/agent-message-proxy.test.ts), [worker branches](../../Workflows/tests/channel-guidance-workflow-branches.test.ts) and [activity retry/skip](../../Workflows/tests/customer-support-retry.test.ts). These cover existing behavior, not AC-31–35, live worker registration or provider delivery.
