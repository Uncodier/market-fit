# Connected accounts in private Robots Ask

**Customer-delegated accounts (local; not deployed).** A manager can delegate the exact private, native Composio account created through the workspace’s hosted authorization flow. OAuth and supported hosted API-key configurations use the same policy; there is no provider allowlist or requirement for a `direct_bindings` record. An explicitly submitted project token remains pinned to that project. A connector's tooling and the provider's own permissions determine what it can do: this does not authorize arbitrary SQL or unrestricted administrative operations.

Workspace members still need use permission. Agents have no default grant, even on workspace-shared accounts. `all` and `selected` set the tool ceiling for each account; a provider denial never selects a different account. Settings may show `authority_kind: "connected_account"` with `attested: false`. Existing narrow OAuth authority and historical receipt access retain their contracts; records created without customer delegation are not upgraded by replay. Reconnect under the new disclosure to delegate such an account.

## Check or stop access for one account

After `20261123165000_connector_ask_host_policy.sql`, **Allow Robots Ask on this account** controls the Ask host in **Tools & permissions**. Check or uncheck it and choose **Save policy**. The separate **Allow use in scheduled tasks** control changes the `direct` host, not Ask. The Ask migration carries existing explicit blocks into the Ask setting. An account can be on but still not authorized for execution; enabling the setting never creates delegation, attestation, or downstream permissions. The local recovery stop action updates the Ask setting. The older controls below describe deployments before that cutover.

Select the intended **Connected account** in **Connectors → Tools & permissions**. For a verified account, enable the connection, allow the interactive assistant, and choose **All compatible tools** or a nonempty list under **Only selected tools**. Save changes to the policy. There is no separate Ask enrollment checkbox. Leaving the assistant host off prevents calls even when tools are selected. Other members cannot inspect or change the manager status.

| Status | Meaning and control |
| --- | --- |
| **Waiting for verification** | Setup is pending, not active. **Cancel automatic setup** records a deliberate block. |
| **Available to authorized members** | The verified account and saved host/tool settings allow Ask. The signed-in member must still have permission for each call. **Turn off Ask access** blocks Ask without disconnecting the account. |
| **Blocked by account or tool settings** (legacy: **On · tools unavailable**) | The account or saved host/tool settings prevent calls. If the server omits the tool mode, the UI says **tool scope unknown** instead. |
| **Turned off by a manager** | Tool, host and sharing edits leave this block intact. To reverse it, first select an enabled account, assistant host and usable tool scope; then choose **Restore Ask access on save** and **Save policy**. |
| **Ask is off · not authorized for execution** | An explicit block and missing account authorization are both present. The restore button remains visible but disabled; editing the host and tools does not grant execution. |
| **Generic provider tools not verified** (legacy: **Off · not verified**) | Neither ordinary OAuth authority nor a current resource attestation is available. A clear-access control does not imply that a grant exists. |
| **Generic provider tools unavailable** (legacy: **Unavailable in Ask**) | The server explicitly marked generic execution unsupported. This cannot be inferred from the account name. |

**Refresh status** reads the saved policy; **Verify provider status** is a separate connection check. On servers that do not report the member-policy contract, the form retains the legacy **Allow Ask to use this account** checkbox for verified accounts. An **Off** status alone does not identify a deliberate block.

Supabase offers **Use a project token for Ask** even when an OAuth configuration exists. OAuth can connect an account but does not bind it to a single project for Ask. The project-token flow records delegation for the exact verified project; it does not grant access to other projects or restore existing account blocks.

The old **Verify and bind this project** action is no longer offered. A delegated account's Ask status already comes from the server; the UI does not read or require the server's private project reference to render the restore control.

If Composio is unavailable, **Manage local account access** on `/connectors` or the toolkit detail page lets a manager cancel setup, turn access off or clear stale consent. It needs the Makinari API and database, not the provider catalogue. It never enables access or switches away from an explicitly requested account. An interrupted save is not confirmation of either outcome. Refresh before acting again; no mutation is automatically retried.

## What the saved permissions allow

Makinari decides **who can request which tools**. The provider enforces **which data the selected credential can read or change**. A read-only token or API key stays read-only under **All compatible tools**, even if the catalogue lists write actions. A credential with write permission still cannot be used through Ask for a tool excluded by Makinari. A provider denial ends that call; it is not retried with another account.

Workspace sharing applies to eligible members, including members added later. No current or future agent inherits access. To authorize an agent, select the exact account and choose **Agent grants → Add agent**. Select the agent, check **Can use subject to policy**, then **Save grant**. To remove access, edit the saved grant and choose **Revoke grant**. Neither change affects another account, even from the same provider.

**Only selected tools** restricts discovery and calls to exact saved IDs; an empty selection allows none. **All compatible tools** includes future eligible provider actions. The legacy catalogue-read setting is no longer editable in the web app; historical settings are not rewritten. Browsing the provider catalogue does not grant Ask access.

In **Connection**, a manager can save a display name shared by account pickers. This does not change the provider credential or make the name a model-facing identifier. In the **Access** footer, a manager can remove all agent grants or all member grants independently. Removing member access also switches that account to explicit grants, stopping inheritance for current and future members. Management access remains; managers can add individual grants again. Removing agents leaves member-based access, including private Ask, unchanged. Neither action cancels work already dispatched. These actions require `20261126000000_connector_account_management.sql` and do not contact the provider.

For example, two CRM connections can list the same action, but only one credential may be able to update the record. Select the intended account in the Ask picker. If multiple accounts fit, Ask should clarify which one you mean before acting. It uses the toolkit and the final eight characters of the local connection ID shown in the picker, **not** the account name, email address, provider account ID or credential. The full local ID identifies the choice if suffixes coincide. Selecting or naming an account is not consent to change it or use another one.

The private, interactive **Ask** session uses the authenticated member’s own instance. The active same-site agent is pinned to that turn for provenance; it cannot lend or withhold connector use. Autonomous Agents retain their own grants; a background run does not inherit the interactive session. Host, workspace, license, location, assigned-record and relevant screen restrictions still apply. Selecting an account narrows the search; it grants nothing. Describe checks the exact account and provider contract; dispatch checks the version, schema and current authority again.

An allowed call is still subject to the provider’s permissions and fees. Private delivery does not hide or reverse a write at its destination. **Allow requests for access** is for members or agents without local permission to use a supported action. It is not a connection setup step, a per-write approval, or a way around the provider’s denial. For a generic Ask tool without a review flow, denial does not create a request. This path does not enable public chat, Customer Support, shared reports, voice, plans or background execution.

In interactive Ask, the model receives the authorized, projected result, not just a receipt. A separate saved provider record is optional; open it while signed in as the requester, or visit `/connectors/results`. The link alone grants nothing. The report is bounded and may omit fields or be truncated. The local Robots and API changes render the private answer in its conversation and allow follow-up analysis with bounded prior tool data or a fresh call on the same authorized connection. Roll out `20261126010000_connector_ask_turn_context.sql` in the API repository before the matching workers. Old answers have no raw tool data to backfill. The latest 20 private reports per owner are available for at most one hour, subject to current authorization. Revoking or replacing the enrollment prevents reopening its direct receipts; re-enabling does not revive them. Do not paste their contents into a shared conversation. If dispatch or delivery is unconfirmed, reconcile in the original system before considering another action: a missing receipt does not mean nothing happened.

## Operator prerequisites (not workspace settings)

An independent deployment operator must verify the **downstream credential**, not just a Composio project or a `PRIVATE` account label. There is no attestation, evidence upload, secret-entry or per-tool version-registration control in this policy UI.

- Verify the canonical external issuer and exact customer-owned business resource dedicated to this site. The downstream provider must enforce that boundary for **every** operation and argument, including after refresh or in-place reauthorization. A site ID, label, URL, account owner’s statement or selected tool list is not evidence. If the boundary cannot be proved, leave the account ineligible.
- Through the approved operator process, register the external resource and applicable Makinari business screens in `connector_result_private.direct_resources`. Use an empty screen list only when no native screen corresponds to the resource. The same issuer/resource cannot be assigned to another site. Multiple isolated accounts can belong to the same site resource.
- The private `direct_attestations` record binds site, connector, toolkit, exact Composio project, provider user binding, account, auth config, credential revision and resource identity to independent evidence and expiry. Record an evidence reference, not secrets. The asserted conditions are `customer_owned_dedicated`, `provider_enforced_single_site`, `business_data_only_no_control_plane` and `reauth_cannot_expand_boundary`. A current proof can authorize member-policy use without writing an enrollment, including on existing accounts. Issuing or renewing proof does not clear a deliberate block.
- Never delegate installation credentials, a shared platform resource, or a credential capable of control-plane administration, cross-site access, credential discovery, arbitrary query/code execution or proxying. For a database resource the canonical external project must be distinct from the verified local installation. A Supabase project reference or broad Management PAT cannot supply this proof; there is no general SQL console. The platform Composio key can be **transport only** with the exact current project binding, not delegated authority over Makinari resources.

Existing OAuth and toolkit-specific onboarding remain separate setup paths. Catalogue coverage is not universal account provisioning.

### Retired shared-project report

The local Ask implementation no longer offers the scoped Makinari metrics report on any account. An old report reference or saved report search cannot start a new read or switch to the native `report` tool. Selecting a connection, enabling legacy catalogue reads, or having a previous receipt does not restore this action. Authorized requesters can still open unexpired historical results at `/connectors/results`; their access checks have not changed.

For rollout, deploy the matching API, worker and web, drain old workers, then apply `20261123090000_retire_instance_scoped_report.sql`. This is a forward-only retirement, not a change to saved connections or OAuth onboarding. It has not been applied as part of this local change.

## Management interface and rollout

**Database cutover (local only):** [`20261123152000_connector_customer_delegation.sql`](../supabase/migrations/20261123152000_connector_customer_delegation.sql) extends the existing `connected_account` authority. Deploy the compatible admission reader and migration before the new callback writer. The verified host calls `connector_finalize_customer_account` with the existing finalization arguments plus `p_auth_scheme`; there is no project argument. Hosted API keys use the same new-account and manager-consent binding as OAuth. For a project token, the server takes the project only from the verified, immutable attempt. A bound project authorizes at most a compatible project-metadata read, not table data, raw SQL, another project, or general management access. Instance and Support still use the v2 admission RPCs, and claim/store/read keep the original attempt ID and turn fence. An unrecognized screen profile requires an unrestricted screen ACL; it is not an empty list of screen requirements.

**Reconnect for new authority.** There is no automatic PAT backfill: the previous token form explicitly excluded Ask execution, and the historical `auth_completed` audit entry identifies the account, actor and revision, not consent to delegate the submitted token. A later project binding or successful sync does not change that. Existing narrowly scoped OAuth rows and existing resource proofs continue to work under their original rules. Reconnect under the new disclosure for the broader account path. A replay cannot issue or restore it. A manager's explicit Ask disable still needs an explicit restore; neither migration nor callback clears it.

The notice-bearing OAuth dialog starts **only** `POST /api/connectors/auth-attempts/ask` with the existing site, toolkit and auth-config identifiers. There is no browser grant, proof, or policy field. The older `/api/connectors/auth-attempts` start and managed OAuth config setup do not delegate a downstream account. For `/api/connectors/supabase-token`, only the new disclosed submission (`delegate_account: true`) records delegation after verification. If the new start fails, do not silently fall back. The [Ask-on-connect migration](../supabase/migrations/20261123030000_connector_ask_on_connect.sql) was applied in the same 07:05 UTC transaction. It is prospective: neither existing account was enrolled. The schema rollout did not deploy the compatible API, worker or web.

On the matching local API, a normal `PATCH /api/connectors/connections/[id]/policy` includes `ask_access: {enabled, expected_direct_revision}` **only for an explicit change**. Unrelated saves omit this field and preserve the saved host and consent. Both the ordinary policy revision and the Ask revision must match. Enabling requires current customer-account authority or a resource attestation, an active enabled connection, the assistant host and a usable tool scope. The atomic receipt must name that account, report the requested `ask_enabled` and advance both revisions by one. An older API or incomplete response is not confirmation: refresh; never retry with a standalone enable. Roll out the matching database function and API before the web. This flow does not backfill grants, enroll unverified accounts, or change existing OAuth onboarding.

`GET /api/connectors/connections/[id]/provider-direct?site_id=<uuid>` and `PATCH /api/connectors/connections/[id]/provider-direct` remain manager-only. PATCH accepts exactly `{site_id, expected_revision, expected_direct_revision, enabled}` and no query parameters. Responses project `{connector_id, revision, direct_revision, attested, enabled}` plus `setup_pending` on the new API. The client also honors `unsupported_reason: "shared_makinari_project"` from older servers. Older responses without `setup_pending` do not confirm pending setup. No proof, project reference or provider data is returned. On member-policy GETs, `authorization_mode: "member_policy"` and `explicitly_disabled` appear together. `enabled` means a current verified binding without an explicit block, **not** permission for a particular host, tool or member. PATCH receipts may omit both markers; reload GET for authority mode after a change. A successful change matches the account and requested boolean, preserves `revision`, advances `direct_revision` by exactly one and leaves no pending setup. A stale revision or missing proof on enable returns `409`; disable requires neither proof nor the catalogue. Direct-only changes invalidate old direct authorizations, not legacy reports.

The [direct policy](../supabase/migrations/20261123010000_connector_provider_direct.sql) and [private receipt](../supabase/migrations/20261123020000_connector_direct_receipts.sql) migrations were applied together to shared Makinari on November 23, 2026, at **05:52:48 UTC**. Do not replay them there. Independent verification found two preserved accounts and **zero direct enrollments**. The matching API, worker and web were not deployed. Before enabling production use, verify eligible and restricted operations, genuine provider denials, revocation, duplicate submission and private receipt delivery on **two separately approved disposable accounts**. No live provider result was established by the schema rollout.
